# OWASP Top 10 2025: IAAA Failures

Esta room introduce tres categorías críticas del OWASP Top 10 (versión 2025) relacionadas con fallos en el modelo **IAAA** (Identity, Authentication, Authorisation, Accountability). Entender estos conceptos es fundamental para asegurar aplicaciones web, ya que son los pilares de cómo se gestionan los usuarios y sus permisos.

## Task 1: Introduction (Introducción)

El **Open Web Application Security Project (OWASP)** es una fundación sin fines de lucro que trabaja para mejorar la seguridad del software. Su "Top 10" es un documento de concientización estándar para desarrolladores y seguridad web, que lista los riesgos de seguridad más críticos.

En esta room, nos enfocamos en las categorías que afectan al modelo IAAA:
1.  **A01: Broken Access Control** (Control de Acceso Roto).
2.  **A07: Identification and Authentication Failures** (Fallos de Identificación y Autenticación).
3.  **A09: Security Logging and Monitoring Failures** (Fallos en el Registro y Monitoreo de Seguridad).

## Task 2: What is IAAA? (¿Qué es IAAA?)

IAAA es un acrónimo que describe el ciclo de vida de la gestión de acceso de un usuario:

1.  **Identity (Identidad):** El identificador único de un usuario (e.g., nombre de usuario, email, ID). Es quién dices ser.
2.  **Authentication (Autenticación):** El proceso de verificar esa identidad (e.g., contraseña, biometría, OTP). Es probar que eres quien dices ser.
3.  **Authorisation (Autorización):** Determinar qué recursos o acciones están permitidos para esa identidad autenticada. Es lo que se te permite hacer.
4.  **Accountability (Responsabilidad/Contabilidad):** El registro y rastreo de las acciones realizadas por la identidad. Es poder demostrar quién hizo qué y cuándo (logs).

**Preguntas clave:**
- **What does IAAA stand for?** Identity, Authentication, Authorisation, Accountability.

## Task 3: A01: Broken Access Control (Control de Acceso Roto)

Esta vulnerabilidad ocurre cuando las restricciones sobre lo que los usuarios autenticados pueden hacer no se aplican correctamente. Los atacantes pueden explotar esto para acceder a datos no autorizados o funciones privilegiadas.

**Conceptos Clave:**
- **IDOR (Insecure Direct Object Reference):** Ocurre cuando una aplicación expone una referencia a un objeto interno de implementación (como un ID de base de datos en la URL `?id=123`) sin controles de acceso. Si cambias el ID y ves los datos de otro usuario, es un IDOR.
- **Escalada de Privilegios Horizontal:** Acceder a datos de otro usuario con el *mismo* nivel de permisos (e.g., Usuario A ve datos de Usuario B).
- **Escalada de Privilegios Vertical:** Acceder a funciones de un usuario con *mayores* permisos (e.g., Usuario estándar accede a panel de Admin).

**Desafío Práctico:**
Se presenta un sitio estático donde puedes manipular el parámetro `accountID` en la URL.
- Al cambiar el ID, puedes ver las cuentas de otros usuarios.
- El objetivo es encontrar al usuario que tiene más de $1 millón.
- **Nota encontrada:** `THM{Found.the.Millionare!}` (probablemente al cambiar el ID a 7 u otro número bajo).

## Task 4: A07: Identification and Authentication Failures (Fallos de Identificación y Autenticación)

Anteriormente conocida como "Broken Authentication", esta categoría cubre fallos en los mecanismos que confirman la identidad del usuario.

**Problemas Comunes:**
- Contraseñas débiles o por defecto.
- Falta de protección contra fuerza bruta (sin bloqueo de cuenta o rate limiting).
- Gestión de sesiones insegura (IDs de sesión predecibles, no invalidar sesiones al salir).
- **Account Confusion (Confusión de Cuentas):** Permitir registrar nombres de usuario que son visualmente o lógicamente similares a cuentas existentes (e.g., registrar `aDmiN` cuando ya existe `admin`), lo que puede confundir al sistema y otorgar acceso a la cuenta original.

**Desafío Práctico:**
- Intentar acceder a la cuenta del administrador (`admin`).
- La vulnerabilidad explotada es permitir registrar un usuario con el mismo nombre pero diferente capitalización (`aDmiN`).
- Al loguearse con la nueva cuenta `aDmiN`, el sistema confunde la identidad y otorga acceso al dashboard del `admin` original.
- **Flag:** `THM{Account.confusion.FTW!}`.

## Task 5: A09: Security Logging and Monitoring Failures (Fallos en Registro y Monitoreo)

Esta categoría se refiere a la falta de capacidad para detectar, escalar y responder a incidentes de seguridad en tiempo real. Sin logs adecuados, los atacantes pueden permanecer en el sistema indefinidamente sin ser detectados.

**Problemas Comunes:**
- No registrar eventos críticos (logins fallidos, transacciones de alto valor).
- Logs almacenados localmente o sin protección (el atacante puede borrarlos).
- Alertas insuficientes o inexistentes.

**Desafío Práctico:**
Se presentan logs de un ataque de fuerza bruta. El objetivo es analizar qué sucedió.

**Análisis de los Logs:**
1.  **Ataque de Fuerza Bruta:** Se observan múltiples intentos fallidos de login desde una misma IP.
    - **IP del atacante:** `203.0.113.45`.
2.  **Acceso Exitoso:** Eventualmente, el atacante logra adivinar la contraseña y obtiene un código de estado exitoso (200 o 302).
    - **Usuario comprometido:** `admin`.
3.  **Acciones Post-Explotación:** Una vez dentro, el atacante intenta acceder a recursos sensibles.
    - **Endpoint accedido:** `/supersecretadminstuff`.

**Conclusión del Módulo:**
La seguridad efectiva requiere una implementación robusta de IAAA:
- **Identidad** única y verificada.
- **Autenticación** fuerte (MFA).
- **Autorización** estricta (principio de menor privilegio).
- **Accountability** total (logs centralizados y monitoreados).
