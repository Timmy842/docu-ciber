# OWASP Top 10 2025: Application Design Flaws

Esta room se centra en cuatro categorías críticas del OWASP Top 10 (versión 2025) relacionadas con fallos en el diseño y arquitectura de las aplicaciones. A diferencia de los errores de código simples, estos problemas surgen de decisiones estructurales deficientes o configuraciones inseguras.

## Task 1: Introduction (Introducción)

El diseño seguro es un requisito fundamental. Los parches de código pueden arreglar bugs, pero no pueden arreglar una arquitectura fundamentalmente insegura. Esta room cubre:
1.  **AS02: Security Misconfigurations** (Configuraciones de Seguridad Incorrectas).
2.  **AS03: Software Supply Chain Failures** (Fallos en la Cadena de Suministro de Software).
3.  **AS04: Cryptographic Failures** (Fallos Criptográficos).
4.  **AS06: Insecure Design** (Diseño Inseguro).

## Task 2: AS02: Security Misconfigurations

Las configuraciones incorrectas ocurren cuando los sistemas se despliegan con valores predeterminados inseguros, configuraciones incompletas o servicios expuestos innecesariamente. No son bugs de programación, sino errores en cómo se configura el entorno.

**Patrones Comunes:**
- Credenciales por defecto no cambiadas.
- Mensajes de error detallados (verbose) que exponen stack traces.
- Almacenamiento en la nube (S3 buckets) públicos.
- Servicios de administración expuestos a internet.

**Desafío Práctico (User Management API):**
- **Objetivo:** Obtener la flag explotando un mensaje de error detallado.
- **Escenario:** Una API permite consultar usuarios por ID (`/api/user/123`).
- **Vulnerabilidad:** Al enviar un input no numérico (e.g., texto "test") en lugar de un ID, la aplicación falla y muestra un "Traceback" completo de Python.
- **Explotación:** El mensaje de error revela el valor de una variable interna o secreto.
- **Flag:** `THM{V3RB0S3_3RR0R_L34K}`.

## Task 3: AS03: Software Supply Chain Failures

Ocurre cuando una aplicación depende de componentes, librerías o servicios de terceros que están comprometidos, desactualizados o no verificados. Los atacantes explotan el eslabón más débil (una dependencia) para comprometer el sistema principal.

**Ejemplos:**
- Usar librerías con vulnerabilidades conocidas (CVEs).
- Ataques tipo SolarWinds (código malicioso inyectado en actualizaciones confiables).
- Dependencia de modelos de IA de terceros sin auditar.

**Desafío Práctico (Data Processing Service):**
- **Objetivo:** Depurar el código desactualizado que importa una librería vieja (`lib/vulnerable_utils.py`).
- **Análisis:** El código fuente muestra un endpoint `/api/process` que acepta JSON. Hay una lógica oculta:
    ```python
    if data == 'debug':
        return jsonify(debug_info())
    ```
- **Explotación:** Enviar una petición POST con `{"data": "debug"}` activa la función de depuración y revela información sensible.
- **Flag:** `THM{SUPPLY_CH41N_VULN3R4B1L1TY}`.

## Task 4: AS04: Cryptographic Failures

Anteriormente conocido como "Sensitive Data Exposure", se refiere a fallos en la protección de datos en tránsito o en reposo debido a criptografía débil o mal implementada.

**Fallos Comunes:**
- Uso de algoritmos obsoletos (MD5, SHA1, DES).
- **Hardcoded Keys:** Claves de cifrado escritas directamente en el código fuente.
- No usar HTTPS o usar protocolos viejos (TLS 1.0).
- Gestión de claves deficiente.

**Desafío Práctico (Secure Document Viewer):**
- **Objetivo:** Descifrar un documento confidencial.
- **Escenario:** Un visor de documentos muestra un texto cifrado y menciona que la función de descifrado no está disponible.
- **Vulnerabilidad:** Inspeccionando el código fuente (o archivos JS accesibles), se encuentra la clave de cifrado "hardcodeada" (incrustada en el código del cliente).
- **Explotación:** Usar la clave encontrada para descifrar el mensaje (posiblemente usando CyberChef o una herramienta similar).
- **Flag:** `THM{CRYPTO_FAILURE_H4RDCOD3D_K3Y}`.

## Task 5: AS06: Insecure Design

El diseño inseguro se refiere a riesgos introducidos por fallos en la arquitectura lógica del sistema, a menudo por falta de modelado de amenazas (Threat Modeling) o por no seguir principios de diseño seguro (como "Secure by Design").

**Diferencia con Errores de Implementación:**
- Un error de implementación es un fallo en el código (e.g., un buffer overflow).
- Un diseño inseguro es una arquitectura que funciona "como se diseñó" pero es inherentemente vulnerable (e.g., preguntas de seguridad para recuperar contraseñas que son fáciles de adivinar mediante OSINT).

**Ejemplo con IA:**
Asumir que un modelo de IA es seguro y permitirle generar consultas SQL o código sin validación es un diseño inseguro.

**Desafío Práctico (SecureChat):**
- **Objetivo:** Explotar una lógica de diseño deficiente en una aplicación de chat.
- **Escenario:** Probablemente involucra manipular el flujo de la aplicación de una manera que los desarrolladores no anticiparon, saltándose pasos de validación o accediendo a funciones administrativas debido a una falta de segmentación adecuada.
